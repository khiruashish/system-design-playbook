    Coding Interview: 12 System-Design Data Structures¶

    Senior system-design loops increasingly include a "now code the core of it" round: the base62 encoder behind the URL shortener, the sliding-window limiter, the Bloom filter in front of the database, the geohash behind "near me", the sketch behind "trending". This tab has the twelve data structures that come up most. Each is a runnable, self-checking Java file in coding-interview/src that asserts its own results (including the error bounds of the probabilistic structures), prints PASS, and is run by CI on every change. The output on each page is real.

    Each page connects the code to the design: where it sits in the architecture, what it costs in memory and time, and what the production version (Redis, Cassandra, Elasticsearch...) adds.

    Each page follows the same structure:

    1. Problem: the statement as an interviewer would give it.
    2. Key idea: the shape of the solution before any code, with a diagram.
    3. Solution: the complete, runnable code (included from the repository, so it is exactly what CI ran).
    4. Walkthrough: the important lines and why they are written that way.
    5. Complexity: time and space for each approach.
    6. Run it: the command and its real output.
    7. Common mistakes and follow-up questions with answers.

    Problem map¶

    # Problem What it tests Level Difficulty
    1 URL Shortener Core: Base62 & Id Allocation Base62 encode/decode, id allocation, custom aliases, overflow safety L1 ★★☆
    2 Sliding-Window Rate Limiter (Log vs Counter) Fixed-window burst problem, sliding log, weighted sliding counter L2 ★★☆
    3 LFU Cache in O(1) Frequency buckets of LinkedHashSet, minFreq tracking, scan resistance L3 ★★★
    4 Bloom Filter: Sizing & Measured False Positives BitSet, optimal m and k, double hashing, no false negatives L2 ★★☆
    5 Snowflake: Distributed Unique Ids Bit layout, sequence per millisecond, clock-backwards handling L2 ★★☆
    6 Geohash: "Restaurants Near Me" Bit interleaving, base32, neighbour cells, haversine filter L3 ★★★
    7 Trending Top-K: Count-Min Sketch + Heap Count-Min Sketch, error bounds, streaming top-K L3 ★★★
    8 Leaderboard: Ranks, Top-N, Neighbours Ordered set, Fenwick tree for ranks, Redis sorted-set semantics L2 ★★☆
    9 Autocomplete: Trie with Cached Top-K Trie, top-K per node, read-optimised writes L2 ★★☆
    10 Merkle Tree: Replica Anti-Entropy Hash tree over key buckets, top-down diff, O(log n) comparisons L3 ★★★
    11 Quorum Replication: R + W > N Tunable consistency, versioned values, read repair, availability L3 ★★★
    12 HyperLogLog: Count Distinct in 16 KB Leading-zero ranks, harmonic mean, small-range correction, mergeable L3 ★★★

    Levels: L1 0–2 yrs · L2 2–5 yrs · L3 5–10 yrs · L4 10+ yrs / architect.

    How to answer a coding round¶

    1. Anchor it in the design: "this sits in the redirect service's hot path, so the lookup must be O(1) and cacheable".
    2. State the budget: memory per item, operations per second, acceptable error. Probabilistic structures are chosen because of these numbers.
    3. Code the core and keep the I/O out. A map stands in for Redis or the DB, and the interviewer wants the algorithm.
    4. Verify with numbers: measured error vs the theoretical bound, keys moved, comparisons made. Each solution prints them.
    5. Name the production equivalent and what it adds: persistence, sharding, replication, TTLs.

    coding-interview/run-all.sh          # runs all 12, writes outputs/
