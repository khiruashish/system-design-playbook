    Glossary¶

    About this glossary

    This glossary has 189 core terms, each with a one-line definition and a link to the chapter that explains it in depth.

    It is checked against the book. GlossaryGen (in labs/appendix-tools/) verifies that every term actually appears in the chapter it links to. Hyphens and spaces count as the same, and there are optional exact-match probes. On the first run, 15 of 159 terms failed:

    • some pointed to the wrong chapter (anycast is covered in Ch 08, not Ch 03; backpressure in Ch 19, not Ch 18);
    • some were phrased differently from the chapter ("outbox pattern" vs "outbox");
    • one described something the chapter doesn't cover. "Fan-out on write vs on read" was reworded to the fan-out Ch 43 actually discusses.

    The current version passes: 189 terms, 0 problems.

    Interview-specific terms are in Chs 57–61. For questions on a term, use the Full Question Index.

    0–9¶

    2PC (two-phase commit)
    Atomic commit protocol: a coordinator asks every participant to prepare, then tells all to commit or all to abort; blocks if the coordinator fails after prepare. → Ch 13 Distributed Transactions
    3-2-1 rule
    Backup rule of thumb: 3 copies, on 2 different media, 1 off-site (or in another region/account). → Ch 27 Reliability & Disaster Recovery

    A¶

    ACID
    Atomicity, Consistency, Isolation, Durability — the guarantees of a database transaction. → Ch 05 Relational Databases Deep Dive
    ADR (architecture decision record)
    A short document recording one decision: context, options, decision, consequences, and when to revisit it. → Ch 31 Architecture Decision Making
    Aggregate
    A cluster of domain objects changed together inside one transaction, with one root that enforces its invariants. → Ch 33 Domain-Driven Design
    Anti-corruption layer
    A translation layer that stops another context's model leaking into yours. → Ch 33 Domain-Driven Design
    Anycast
    One IP address announced from many locations; the network routes each client to the nearest. → Ch 08 Load Balancing, Proxies & Gateways
    API gateway
    Edge component that routes, authenticates, rate-limits and shapes requests for backend services. → Ch 08 Load Balancing, Proxies & Gateways
    At-least-once delivery
    Every message is delivered one or more times; consumers must tolerate duplicates. → Ch 14 Messaging & Event Streaming
    At-most-once delivery
    Every message is delivered zero or one time; losses are possible, duplicates are not. → Ch 14 Messaging & Event Streaming
    Availability
    The fraction of time (or requests) a system serves correctly, often expressed in "nines". → Ch 01 What System Design Is
    Avro
    A binary serialization format with reader and writer schemas resolved at read time. → Ch 28 Schema & Data Evolution

    B¶

    Back-of-the-envelope estimate
    A quick order-of-magnitude calculation of load, storage or bandwidth to guide design choices. → Ch 02 Back-of-the-Envelope Estimation
    Backfill
    Populating a new column or store with historical data, usually in batches alongside live writes. → Ch 28 Schema & Data Evolution
    Backpressure
    Signalling upstream to slow down when a component cannot keep up, instead of queueing without bound. → Ch 19 Concurrency at Scale in Java
    Base62
    Encoding numbers with 0–9, a–z and A–Z, used for short URL codes. → Ch 38 Case Study: URL Shortener & SMS Short Links
    BFF (backend for frontend)
    A backend tailored to one client type (app, web) that aggregates and shapes calls for it. → Ch 34 Modern Architecture Styles
    Blast radius
    How many users or systems one failure or bad change can affect. → Ch 27 Reliability & Disaster Recovery
    Bloom filter
    A compact probabilistic set: "definitely not present" or "probably present", with a tunable false-positive rate. → Ch 53 Case Study: Web Crawler (Competitor Price Monitoring)
    Blue-green deployment
    Running two production environments and switching traffic from the old (blue) to the new (green) at once. → Ch 26 Deployment & Infrastructure
    BM25
    A standard relevance-scoring function based on term frequency, document frequency and document length. → Ch 22 Search Systems
    Bounded context
    A boundary within which a model and its language are consistent; the unit of ownership in DDD. → Ch 33 Domain-Driven Design
    Bulkhead
    Isolating resources (threads, connections, pools) per dependency so one failure cannot exhaust all. → Ch 18 Resilience Patterns

    C¶

    Cache stampede
    Many requests miss the same expired key at once and overload the source; prevented by locking, coalescing or early refresh. → Ch 07 Caching
    Cache-aside
    The application reads the cache, falls back to the database on a miss, and fills the cache itself. → Ch 07 Caching
    Calibration (interviewers)
    Aligning interviewers' scoring through anchored rubrics and shared review so verdicts are consistent. → Ch 60 Mock Interviews
    Canary release
    Sending a small share of traffic to a new version and widening only if its metrics stay healthy. → Ch 26 Deployment & Infrastructure
    CAP theorem
    During a network partition a distributed store must choose between consistency and availability. → Ch 12 Consistency, Time & Consensus
    CDC (change data capture)
    Streaming a database's committed changes (usually from its log) to other systems. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing
    CDN (content delivery network)
    Edge caches close to users that serve static and cacheable content. → Ch 52 Case Study: Object Storage & Media Pipeline
    Cell-based architecture
    Splitting a system into independent full copies (cells), each serving a subset of users, to bound blast radius. → Ch 34 Modern Architecture Styles
    Chaos engineering
    Deliberately injecting failures in controlled experiments to verify resilience. → Ch 27 Reliability & Disaster Recovery
    Choreography
    Services react to each other's events without a central coordinator. → Ch 34 Modern Architecture Styles
    Circuit breaker
    Stops calling a failing dependency for a while after errors exceed a threshold, then probes before resuming. → Ch 18 Resilience Patterns
    Clock skew
    The difference between clocks on different machines; why wall-clock timestamps cannot order distributed events safely. → Ch 12 Consistency, Time & Consensus
    Connection pool
    A bounded set of reused database connections; its size is a key capacity limit. → Ch 05 Relational Databases Deep Dive
    Consistent hashing
    Mapping keys and nodes onto a ring so adding or removing a node moves only a small share of keys. → Ch 11 Partitioning & Sharding
    Consumer group
    Kafka consumers sharing a group id divide a topic's partitions among themselves. → Ch 14 Messaging & Event Streaming
    Consumer lag
    How far a consumer is behind the latest message in a partition. → Ch 14 Messaging & Event Streaming
    Contract testing
    Verifying that a provider still satisfies the requests and responses its consumers depend on (e.g. Pact). → Ch 29 Testing Distributed Systems
    Coordinated omission
    A load-testing error where a stalled system also stalls request sending, hiding the real latency. → Ch 25 Performance Engineering
    Cost per order
    A unit-economics metric: infrastructure cost divided by orders served. → Ch 35 Cost Engineering & FinOps
    Count-Min Sketch
    A small probabilistic table that estimates item frequencies in a stream, never underestimating. → Ch 51 Case Study: Real-time Analytics & Top-K (Trending)
    CQRS
    Command Query Responsibility Segregation: separate models for writes and for reads. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing
    CRDT
    A conflict-free replicated data type whose replicas can merge concurrent updates deterministically. → Ch 10 Replication
    Crypto-shredding
    Making data unreadable by deleting its encryption key, used for erasure in backups and logs. → Ch 36 Compliance, Governance & Data Residency

    D¶

    DAG (workflow)
    A directed acyclic graph of jobs where each runs after its dependencies succeed. → Ch 50 Case Study: Distributed Job Scheduler
    Dark store
    A delivery-only warehouse serving quick-commerce orders from a small area. → Ch 46 Case Study: Grocery Checkout & Inventory Reservation
    Data residency
    A requirement that certain data be stored (and sometimes processed) within a given country or region. → Ch 36 Compliance, Governance & Data Residency
    Dead-letter queue
    A queue that holds messages that repeatedly fail processing, for inspection and replay. → Ch 14 Messaging & Event Streaming
    Deterministic simulation testing
    Running a whole distributed system in a simulated, seeded environment so failures can be reproduced exactly. → Ch 29 Testing Distributed Systems
    Disagree and commit
    Arguing a position with evidence before a decision, then fully supporting the decision once made. → Ch 61 Behavioural & Leadership
    Distributed lock
    A lock shared across processes; safe only with leases and fencing tokens. → Ch 20 Idempotency, IDs & Distributed Locks
    Distributed monolith
    Services that must be deployed or changed together — the costs of microservices without the independence. → Ch 34 Modern Architecture Styles
    DLQ
    See dead-letter queue. → Ch 14 Messaging & Event Streaming
    DNS
    The Domain Name System, mapping names to addresses through a hierarchy of cached lookups. → Ch 03 Networking Essentials
    Domain event
    A record that something meaningful happened in the domain, named in the past tense. → Ch 33 Domain-Driven Design
    Double-entry ledger
    Recording every money movement as equal debits and credits so balances always reconcile. → Ch 45 Case Study: Payment System
    Durability
    Once acknowledged, data survives crashes and failures. → Ch 01 What System Design Is

    E¶

    Erasure coding
    Splitting data into k data and m parity shards so any k of k+m can rebuild it, at lower overhead than replication. → Ch 52 Case Study: Object Storage & Media Pipeline
    Error budget
    The allowed unreliability under an SLO (e.g. 0.1% of requests); spending it slows releases. → Ch 24 Observability
    Event sourcing
    Storing state as the sequence of events that produced it; current state is derived by replay. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing
    Event storming
    A workshop technique that maps a domain by laying out its events on a timeline. → Ch 33 Domain-Driven Design
    Eventual consistency
    Replicas converge to the same value if updates stop; reads may be stale meanwhile. → Ch 12 Consistency, Time & Consensus
    Exactly-once processing
    Each input affects the output once, achieved by combining at-least-once delivery with idempotency or transactions. → Ch 14 Messaging & Event Streaming
    Expand/contract
    Changing a schema in backward-compatible steps: add the new, migrate, switch, then remove the old. → Ch 28 Schema & Data Evolution

    F¶

    Failover
    Moving service from a failed component (e.g. a primary database) to a standby. → Ch 27 Reliability & Disaster Recovery
    Fan-out
    One request or event multiplied into many downstream calls or writes — a feed request into feature lookups, or a post into every follower's feed. → Ch 43 Case Study: Home Feed & Recommendations
    Feature flag
    A runtime switch that turns code paths on or off without redeploying. → Ch 26 Deployment & Infrastructure
    Fencing token
    A monotonically increasing number checked by the resource, so a stale lock holder's writes are rejected. → Ch 20 Idempotency, IDs & Distributed Locks
    Fitness function
    An automated check that an architectural property (dependency rules, latency, cost) still holds. → Ch 31 Architecture Decision Making
    Flip point
    The weighting or value at which a decision matrix would choose a different option. → Ch 31 Architecture Decision Making

    G¶

    Geohash
    Encoding latitude and longitude into a string whose shared prefixes mean nearby cells. → Ch 47 Case Study: Delivery Dispatch & Live Tracking
    Graceful degradation
    Keeping the core function working with reduced features when dependencies fail. → Ch 18 Resilience Patterns
    gRPC
    A high-performance RPC framework using HTTP/2 and Protocol Buffers. → Ch 04 API Design

    H¶

    Head-of-line blocking
    One slow item holding up everything behind it on a connection or queue. → Ch 03 Networking Essentials
    Heartbeat
    A periodic signal that a node is alive, used for failure detection. → Ch 12 Consistency, Time & Consensus
    Hedged request
    Sending a duplicate request after a delay and using whichever answer returns first, to cut tail latency. → Ch 25 Performance Engineering
    Hexagonal architecture
    Ports and adapters: domain logic at the centre, infrastructure plugged in through interfaces. → Ch 34 Modern Architecture Styles
    Hinted handoff
    A node temporarily stores writes for an unavailable replica and forwards them when it returns. → Ch 54 Case Study: Distributed Key-Value Store
    Hot key / hot partition
    A key or shard receiving a disproportionate share of traffic. → Ch 11 Partitioning & Sharding
    HyperLogLog
    A probabilistic structure that estimates the number of distinct items in a few kilobytes. → Ch 51 Case Study: Real-time Analytics & Top-K (Trending)

    I¶

    Idempotency key
    A client-supplied key that lets the server recognise retries and return the original result. → Ch 20 Idempotency, IDs & Distributed Locks
    Idempotent
    An operation that has the same effect whether applied once or many times. → Ch 20 Idempotency, IDs & Distributed Locks
    Interviewer card
    A mock interviewer's sheet: prompt, hidden requirements, follow-up chains, curveball, level anchors. → Ch 60 Mock Interviews
    Invariant
    A rule that must always hold, e.g. "stock never goes below zero". → Ch 33 Domain-Driven Design
    Inverted index
    A map from each term to the documents containing it; the core structure of full-text search. → Ch 22 Search Systems
    Isolation level
    How much concurrent transactions can see of each other (read committed, repeatable read, serializable). → Ch 05 Relational Databases Deep Dive

    J¶

    Jitter
    Randomness added to retry delays so clients don't retry in synchronized waves. → Ch 18 Resilience Patterns
    Journey SLO
    A reliability objective for an end-to-end user journey (e.g. checkout), composed from the services it touches. → Ch 56 Capstone: The Grocery Marketplace, End to End
    JWT
    JSON Web Token: a signed, self-contained token carrying claims about a subject. → Ch 23 Security Architecture

    K¶

    Kafka partition
    An ordered, append-only log within a topic; the unit of ordering and parallelism. → Ch 14 Messaging & Event Streaming

    L¶

    L4 / L7 load balancing
    Balancing on transport-level connections (L4) versus on application requests such as HTTP (L7). → Ch 08 Load Balancing, Proxies & Gateways
    Lamport clock
    A logical counter that orders events consistently with causality. → Ch 12 Consistency, Time & Consensus
    Latency
    The time to complete one operation, reported as percentiles (p50, p99). → Ch 01 What System Design Is
    Leader election
    Choosing one node to act as coordinator, typically through consensus or a lease. → Ch 12 Consistency, Time & Consensus
    Leader lease
    A time-limited leadership grant; a leader stops acting when its lease may have expired. → Ch 50 Case Study: Distributed Job Scheduler
    Leaky bucket
    A rate limiter that drains requests at a constant rate, smoothing bursts. → Ch 39 Case Study: Distributed Rate Limiter
    Lease
    A time-limited grant (e.g. a lock) that expires unless renewed. → Ch 20 Idempotency, IDs & Distributed Locks
    Level expectations (B1–B4)
    What an interviewer expects at engineer, senior, staff and principal level in scope, depth and judgement. → Ch 58 Level Expectations: From Engineer to Principal
    Linearizability
    Every operation appears to take effect instantly at one point between its start and end, in real-time order. → Ch 12 Consistency, Time & Consensus
    Little's Law
    Items in a system = arrival rate × time in system (L = λW). → Ch 31 Architecture Decision Making
    Load shedding
    Rejecting some requests early under overload so the rest succeed. → Ch 18 Resilience Patterns
    LSM tree
    A log-structured merge tree: writes go to memory and immutable sorted files that are merged in the background. → Ch 54 Case Study: Distributed Key-Value Store

    M¶

    Merkle tree
    A hash tree used to find differing ranges between replicas cheaply. → Ch 54 Case Study: Distributed Key-Value Store
    Microservices
    Independently deployable services organised around business capabilities. → Ch 16 Microservices Architecture
    Modular monolith
    One deployable with strictly enforced internal module boundaries. → Ch 34 Modern Architecture Styles
    mTLS
    Mutual TLS: both client and server authenticate with certificates. → Ch 23 Security Architecture
    Multi-tenancy
    One system serving many customers (tenants) with isolation of data and performance. → Ch 30 Multi-Tenancy & SaaS Architecture
    Multipart upload
    Uploading a large object in independently retried parts that are assembled at the end. → Ch 52 Case Study: Object Storage & Media Pipeline
    MVCC
    Multi-version concurrency control: readers see a snapshot while writers create new row versions. → Ch 05 Relational Databases Deep Dive

    N¶

    Noisy neighbor
    A tenant or workload consuming shared resources and degrading others. → Ch 30 Multi-Tenancy & SaaS Architecture

    O¶

    OAuth 2.0
    A delegation protocol for obtaining access tokens; OpenID Connect adds identity on top. → Ch 23 Security Architecture
    Observability
    Understanding a system's internal state from its outputs: metrics, logs and traces. → Ch 24 Observability
    Optimistic locking
    Detecting conflicting updates with a version check at write time instead of locking upfront. → Ch 05 Relational Databases Deep Dive
    Orchestration
    A central coordinator tells services what to do and tracks the workflow. → Ch 34 Modern Architecture Styles
    Order book
    The list of resting buy and sell orders for an instrument, sorted by price and time. → Ch 55 Case Study: Order Matching Engine
    Outbox pattern
    Writing an event to an outbox table in the same transaction as the business change, then relaying it. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing

    P¶

    p99 / tail latency
    The latency under which 99% of requests complete; the slow tail users notice. → Ch 25 Performance Engineering
    PACELC
    Extends CAP: if Partitioned choose Availability or Consistency, Else choose Latency or Consistency. → Ch 12 Consistency, Time & Consensus
    Pagination (cursor / keyset)
    Returning results in pages using a position marker rather than an offset. → Ch 04 API Design
    Paved road
    The supported, easiest path for building services, adopted because it saves effort. → Ch 31 Architecture Decision Making
    Paxos
    A family of consensus protocols for agreeing on values despite failures. → Ch 12 Consistency, Time & Consensus
    PCI DSS
    The card-industry security standard; scope shrinks when card data never touches your systems. → Ch 36 Compliance, Governance & Data Residency
    PITR (point-in-time recovery)
    Restoring a database to any moment by replaying archived logs onto a base backup. → Ch 27 Reliability & Disaster Recovery
    Politeness (crawler)
    Limiting request rate per host so a crawler does not overload the sites it visits. → Ch 53 Case Study: Web Crawler (Competitor Price Monitoring)
    Polyglot persistence
    Using different datastores for different access patterns within one system. → Ch 06 NoSQL & Polyglot Persistence
    Postmortem (blameless)
    A written incident review focused on systemic causes and actions, not individual blame. → Ch 27 Reliability & Disaster Recovery
    Price-time priority
    Matching rule: best price first, and among equal prices, the earliest order first. → Ch 55 Case Study: Order Matching Engine
    Priority lane
    A separate queue and worker pool for urgent traffic so bulk work cannot delay it. → Ch 40 Case Study: Notification System
    Property-based testing
    Tests that check properties over many generated inputs, shrinking failures to minimal cases. → Ch 29 Testing Distributed Systems
    Protobuf
    Protocol Buffers: a binary format whose field numbers enable backward-compatible evolution. → Ch 28 Schema & Data Evolution

    Q¶

    Quorum
    The minimum number of replicas (R, W) that must respond; R + W > N gives overlapping reads and writes. → Ch 10 Replication

    R¶

    Raft
    A consensus algorithm based on an elected leader replicating a log to a majority. → Ch 12 Consistency, Time & Consensus
    Rate limiting
    Capping how many requests a client may make per time window. → Ch 39 Case Study: Distributed Rate Limiter
    Read model (materialized view)
    A query-optimised copy of data, kept up to date from events or changes, that serves reads in CQRS. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing
    Read replica
    A copy of the database that serves reads, usually asynchronously updated. → Ch 10 Replication
    Read-your-writes
    A guarantee that a user sees their own writes immediately. → Ch 10 Replication
    Reconciliation
    Comparing records between two systems (e.g. ledger vs settlement file) and resolving differences. → Ch 45 Case Study: Payment System
    Reed-Solomon
    The erasure code used in many storage systems. → Ch 52 Case Study: Object Storage & Media Pipeline
    Replication lag
    How far a replica is behind the primary; bounds stale reads and data loss on failover. → Ch 10 Replication
    Reservation (inventory)
    Temporarily holding stock for a checkout until payment succeeds or the hold expires. → Ch 46 Case Study: Grocery Checkout & Inventory Reservation
    Retry storm
    Retries from many clients amplifying load on an already failing service. → Ch 18 Resilience Patterns
    Rightsizing
    Matching instance sizes to actual utilisation. → Ch 35 Cost Engineering & FinOps
    Robots.txt
    A site's file stating which paths crawlers may fetch; honouring it is part of polite crawling. → Ch 53 Case Study: Web Crawler (Competitor Price Monitoring)
    Row-Level Security (RLS)
    Database-enforced filtering of rows by tenant or user. → Ch 30 Multi-Tenancy & SaaS Architecture
    RPO / RTO
    Recovery Point Objective (acceptable data loss) and Recovery Time Objective (acceptable downtime). → Ch 27 Reliability & Disaster Recovery
    Rubric
    The scoring dimensions and anchors interviewers use to rate a system design answer. → Ch 57 The System Design Interview Framework

    S¶

    Saga
    A sequence of local transactions with compensating actions instead of a distributed commit. → Ch 13 Distributed Transactions
    Saga compensation
    The undo step for a completed saga step, run when a later step fails. → Ch 56 Capstone: The Grocery Marketplace, End to End
    Schema registry
    A service storing message schemas and enforcing compatibility rules. → Ch 28 Schema & Data Evolution
    Serializable
    The strongest isolation level: the result equals some serial order of the transactions. → Ch 05 Relational Databases Deep Dive
    Service mesh
    A layer of sidecar proxies handling traffic, security and telemetry between services. → Ch 17 Inter-Service Communication
    Settlement
    The payment provider transferring collected funds to the merchant, usually in daily batches with a report. → Ch 45 Case Study: Payment System
    Sharding
    Splitting data across independent database nodes by a shard key. → Ch 11 Partitioning & Sharding
    Sidecar
    A helper process deployed next to each service instance (proxy, agent). → Ch 17 Inter-Service Communication
    Signed URL (presigned URL)
    A time-limited URL that lets a client upload or download an object directly from storage. → Ch 52 Case Study: Object Storage & Media Pipeline
    SLI / SLO / SLA
    Indicator (what you measure), objective (the target), agreement (the contractual promise). → Ch 24 Observability
    Sliding window (rate limiting)
    Counting requests over a rolling time window rather than fixed buckets, avoiding boundary bursts. → Ch 39 Case Study: Distributed Rate Limiter
    Sloppy quorum
    Accepting writes on any reachable nodes during failures, reconciled later. → Ch 54 Case Study: Distributed Key-Value Store
    Snowflake ID
    A 64-bit, roughly time-ordered ID built from a timestamp, a worker id and a sequence number. → Ch 20 Idempotency, IDs & Distributed Locks
    Spaced repetition
    Reviewing material at growing intervals, timed to just before it would be forgotten. → Ch 59 Interview Q&A Bank
    Split brain
    Two nodes both believing they are the primary and accepting conflicting writes. → Ch 27 Reliability & Disaster Recovery
    Spot instance
    Discounted spare cloud capacity that can be reclaimed at short notice. → Ch 35 Cost Engineering & FinOps
    SSTable
    Sorted String Table: an immutable sorted file of key-value pairs in an LSM tree. → Ch 54 Case Study: Distributed Key-Value Store
    STAR
    Situation, Task, Action, Result — the standard structure for behavioural answers (this handbook adds Learning). → Ch 61 Behavioural & Leadership
    Story bank
    A set of prepared, tagged career stories covering the competencies interviewers probe at your level. → Ch 61 Behavioural & Leadership
    Strangler fig
    Migrating gradually by routing features one by one from the old system to the new. → Ch 16 Microservices Architecture
    Structured concurrency
    Treating concurrent subtasks as one unit with a shared lifetime, cancellation and error handling. → Ch 19 Concurrency at Scale in Java

    T¶

    Throughput
    Operations completed per unit time. → Ch 01 What System Design Is
    Thundering herd
    Many waiting clients woken or retrying at once, overwhelming a resource. → Ch 07 Caching
    Token bucket
    A rate-limiting algorithm that refills tokens at a fixed rate and allows bursts up to bucket size. → Ch 39 Case Study: Distributed Rate Limiter
    Top-K / heavy hitters
    The most frequent items in a stream, often estimated with sketches. → Ch 51 Case Study: Real-time Analytics & Top-K (Trending)
    Tracing (distributed)
    Following a request across services as a tree of timed spans. → Ch 24 Observability
    Transactional outbox
    See outbox pattern. → Ch 15 Event-Driven Architecture, CQRS & Event Sourcing
    Trie
    A prefix tree; each path from the root spells a prefix, which makes prefix lookups fast for autocomplete. → Ch 42 Case Study: Search Autocomplete (Typeahead)
    TTL
    Time to live: how long a cached or stored item remains valid. → Ch 07 Caching
    Two-way door
    A reversible decision that can be made quickly; a one-way door deserves more care. → Ch 31 Architecture Decision Making

    U¶

    Ubiquitous language
    The shared vocabulary of a bounded context, used in both conversation and code. → Ch 33 Domain-Driven Design
